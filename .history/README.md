# 🗂️ Dossier `.history` — Archivage YnFOR

Le dossier `.history/` contient **l’historique complet du projet YnFOR**, organisé de manière professionnelle et durable.  
Il centralise toutes les informations liées aux versions, aux milestones, aux issues et aux releases, afin de garantir une traçabilité claire et une gestion propre de l’évolution du projet.

Ce dossier est **interne**, **structuré**, et **séparé du code**, ce qui permet de maintenir un dépôt propre et professionnel.

---

# 📁 Structure du dossier

```
.history/
 ├─ milestones/
 ├─ issues/
 └─ releases/
```

---

## 📌 1. `milestones/`
Contient toutes les **milestones** du projet, versionnées et datées.

Exemples :
- `v1.0.0.md`
- `v1.2.0.md`
- `v1.5.0.md`
- `v2.0.0.md`

Chaque fichier décrit :
- les objectifs de la version  
- les tâches associées  
- l’état d’avancement  
- les cases cochées  

---

## 📌 2. `issues/`
Contient les **issues importantes**, documentées en Markdown.

Exemples :
- `issue_v1.5.0_global.md`
- `issue_brand_identity.md`
- `issue_tests_e2e.md`

Chaque issue inclut :
- description  
- portée  
- tâches  
- checklist  
- milestone liée  

---

## 📌 3. `releases/`
Contient toutes les **notes de release** du projet.

Exemples :
- `release_v1.0.0.md`
- `release_v1.2.0.md`
- `release_v1.5.0.md`

Chaque release inclut :
- nouveautés  
- améliorations  
- correctifs  
- fichiers inclus  
- statut de la version  

---

# 🎯 Objectif du dossier `.history`

- Centraliser l’historique du projet  
- Documenter chaque version de manière claire  
- Faciliter la maintenance et la contribution  
- Offrir une vision complète de l’évolution du projet  
- Séparer proprement le code et la documentation historique  

---

# 🧩 Bonnes pratiques YnFOR

- Un fichier par version (milestone / release)  
- Un fichier par issue majeure  
- Toujours utiliser un nom clair et versionné  
- Garder les cases cochées pour les tâches terminées  
- Mettre à jour `CHANGELOG.md` et `ROADMAP.md` en parallèle
